Kotikassa

A family personal finance application for tracking expenses (via receipt scanning), income, savings, and investments. Built for Finnish households, with full support for Finnish-language receipts from stores like S-Market, K-Market, Lidl, and Prisma.

Web + Mobile Multi-tenant (per family) Low fixed infrastructure cost TypeScript · React · Supabase GPT receipt extraction

Technology Choices

Tech Stack

Every technology was chosen for a specific reason. The guiding principle: modern, TypeScript-first, privacy-aware, and minimal operational overhead. Most infrastructure uses free tiers; receipt extraction is a measured usage-based service.

Frontend — Web

TechnologyPurposeWhy this, not alternatives
Next.js 14 (App Router)Web application frameworkBest-in-class React framework. App Router enables server components, reducing JS sent to browser. Deployed on Vercel with zero config. Alternatives: Remix (good but smaller ecosystem), Vite+React (no SSR out of the box).
TypeScriptType safety across all codeCatches bugs at compile time. Shared types between frontend, mobile, and backend. No alternative considered — TypeScript is mandatory for a maintainable multi-file project.
Tailwind CSSUtility-first stylingNo CSS files to maintain. Consistent design system. Works perfectly with Next.js. Alternative: CSS Modules (more verbose), Styled Components (runtime overhead).
shadcn/uiUI component libraryCopy-paste components built on Radix UI primitives. Fully accessible, fully customizable (you own the code). No npm dependency lock-in. Alternative: MUI (opinionated, harder to customize), Chakra UI (less control).
TanStack Query (React Query)Server state managementHandles caching, refetching, optimistic updates, and loading states for all API calls. Eliminates boilerplate. Alternative: SWR (simpler but less powerful), Redux Toolkit Query (heavier).
ZustandClient state managementTiny (1KB), simple API, TypeScript-native. Only for UI state not tied to the server (modals, selected filters). Alternative: Redux (too heavy for this), Context API (performance issues with re-renders).

Data Architecture

Multi-tenancy Model

Kotikassa is a multi-tenant application where each tenant is a family. Multiple families use the same application and database infrastructure, but each family's data is completely invisible to all other families — enforced at the database level.

What is multi-tenancy?

A multi-tenant application serves multiple independent groups (tenants) from a single deployed instance. Think of it like an apartment building: one building, many apartments, each fully private. This is different from a single-user app (a house) or separate deployments per user (separate buildings).

For Kotikassa: each family is one tenant. The Virtanen family cannot see the Mäkinen family's expenses, receipts, or savings goals — even though all data lives in the same PostgreSQL database.

✅ What families share

  • • The application code and UI
  • • The database infrastructure (server)
  • • The hosting platform (Vercel, Supabase)

🔒 What families never share

  • • Expenses, receipts, and items
  • • Income and savings data
  • • Categories and budgets
  • • Receipt images
  • • Any other user data

How isolation is enforced — Row Level Security (RLS)

Data isolation is enforced using PostgreSQL's Row Level Security (RLS) — a database-native feature. Every table has a family_id column, and RLS policies prevent any query from returning rows where family_id doesn't match the authenticated user's family.

This means even if there's a bug in the application code, the database itself will refuse to return another family's data. The protection is at the lowest possible layer.

-- Example RLS policy on expense_items table
ALTER TABLE expense_items ENABLE ROW LEVEL SECURITY;

-- Users can only see expense items belonging to their family
CREATE POLICY "family_isolation" ON expense_items
  FOR ALL
  USING (
    family_id = (
      SELECT family_id FROM profiles
      WHERE id = auth.uid()  -- auth.uid() = logged-in user's ID
    )
  );
Security by default: Supabase applies RLS to every client-side request. Server-side Edge Functions can use a service role key to bypass RLS when needed (e.g., sending budget alert emails across all families).

Security

Authentication & Authorization

Authentication (who are you?) is handled by Supabase Auth. Authorization (what can you do?) is enforced by PostgreSQL Row Level Security policies and application-level role checks.

Authentication methods

📧 Email + Password

Standard sign up with email verification. Password is hashed by Supabase (bcrypt). Users can reset password via email link.

🔑 Google OAuth

"Sign in with Google" — faster for users who prefer it. Uses the same Supabase session system as email/password.

🔗 Magic Link

Passwordless login via email link. Optional — useful for family members who don't want to manage a password.

✉️ Family Invite ✅

Not a login method — a one-time link that joins the recipient into the admin's family. Invite links expire after 48 hours and are single-use.

Flow: Admin clicks "Generate invite link" in Settings → shares URL (/join?token=xxx) → recipient visits page → sees family name preview (preview_invite() SECURITY DEFINER RPC) → creates account or logs in → clicks "Accept" → use_invite() joins them to the family. Both functions bypass RLS safely; no service role key needed in the app.

Session management

Supabase Auth issues a JWT (JSON Web Token) on login. The JWT contains the user's ID (sub), email, and expiry. It is stored in a secure httpOnly cookie (web) or SecureStore (mobile). The JWT is automatically refreshed by the Supabase client library.

Every database request includes the JWT. Supabase extracts auth.uid() from it, which RLS policies use to enforce data isolation.

Data Layer

Database Schema

PostgreSQL relational schema. All tables have family_id for tenant isolation and Row Level Security enabled. UUIDs are used for all primary keys to avoid enumeration attacks.

-- Tenant root: every other table references this
CREATE TABLE families (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  name        text NOT NULL,
  currency    text NOT NULL DEFAULT 'EUR', -- ISO 4217 code; admin-configurable (EUR/USD/LKR/DKK)
  created_at  timestamptz DEFAULT now()
);

-- One profile per user (extends Supabase auth.users)
CREATE TABLE profiles (
  id            uuid PRIMARY KEY REFERENCES auth.users,
  family_id     uuid REFERENCES families,
  display_name  text,
  role          text DEFAULT 'member', -- 'admin' | 'member'
  avatar_url    text,
  preferences   jsonb NOT NULL DEFAULT '{}', -- JSONB bag of UI prefs (showWeekFilter, showStoreFilter...)
                                              -- resolved in app via resolvePreferences() — no migration needed for new keys
  created_at    timestamptz DEFAULT now()
);

-- Expense categories (customizable per family)
CREATE TABLE categories (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id   uuid NOT NULL REFERENCES families,
  name        text NOT NULL,
  icon        text,
  color       text,
  sort_order  int  DEFAULT 0,
  created_at  timestamptz DEFAULT now()
);

-- Raw receipt records (one per photo)
CREATE TABLE receipts (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id       uuid NOT NULL REFERENCES families,
  uploaded_by     uuid REFERENCES profiles,
  image_url       text,           -- Supabase Storage path
  store_name      text,
  receipt_date    date,
  total_amount    numeric(10,2),
  ocr_raw_text    text,           -- legacy Phase 2 output
  ocr_confidence  numeric(5,2),   -- legacy; null for GPT scans
  scan_provider       text,
  scan_model          text,
  scan_prompt_version text,
  scan_schema_version text,
  scan_raw_result     jsonb,      -- validated original model JSON
  scan_latency_ms     integer,
  scan_input_tokens   integer,
  scan_output_tokens  integer,
  training_eligible        boolean DEFAULT false,
  training_consent_version text,
  training_consented_at    timestamptz,
  status          text DEFAULT 'pending_review', -- 'pending_review'|'confirmed'|'manual'
  created_at      timestamptz DEFAULT now()
);

-- Individual expense line items (the core table)
CREATE TABLE expense_items (
  id                   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id            uuid NOT NULL REFERENCES families,
  receipt_id           uuid REFERENCES receipts,          -- NULL if manual entry
  recurring_expense_id    uuid REFERENCES recurring_expenses, -- NULL if not from a recurring template
  people_transaction_id   uuid REFERENCES people_transactions ON DELETE CASCADE, -- NULL if not linked to a People transaction
  added_by             uuid REFERENCES profiles,
  category_id          uuid REFERENCES categories,
  catalog_item_id      uuid REFERENCES catalog_items, -- canonical reporting identity
  name                 text NOT NULL,
  amount               numeric(10,2) NOT NULL,
  quantity             numeric(10,3) DEFAULT 1,
  unit                 text,                -- 'kg', 'kpl', 'g', 'l'
  discount_amount      numeric(10,2),       -- saving vs. original (from ALE/discount on receipt)
  original_price       numeric(10,2),       -- amount + discount_amount; shown as strikethrough
  expense_date         date NOT NULL,
  is_manual            boolean DEFAULT false,
  is_on_receipt        boolean,             -- label quality, not training consent
  receipt_line_index   integer,             -- deterministic receipt order
  notes                text,
  created_at           timestamptz DEFAULT now()
);

-- Canonical household product identities for unit-safe item reports
CREATE TABLE catalog_items (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id       uuid NOT NULL REFERENCES families,
  canonical_name  text NOT NULL,
  normalized_name text NOT NULL,
  UNIQUE (family_id, normalized_name)
);

CREATE TABLE catalog_item_aliases (
  id               uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id        uuid NOT NULL REFERENCES families,
  catalog_item_id  uuid NOT NULL REFERENCES catalog_items,
  alias_name       text NOT NULL,
  normalized_alias text NOT NULL,
  UNIQUE (family_id, normalized_alias)
);

-- Recurring expense templates (fixed monthly obligations, subscriptions, loans)
-- Instances are materialized into expense_items on expenses page load for the current month.
CREATE TABLE recurring_expenses (
  id                      uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id               uuid NOT NULL REFERENCES families,
  created_by              uuid NOT NULL REFERENCES profiles,
  name                    text NOT NULL,
  amount                  numeric(10,2) NOT NULL CHECK (amount >= 0),
  category_id             uuid REFERENCES categories ON DELETE SET NULL,
  recurrence_type         text NOT NULL DEFAULT 'monthly',
  day_of_month            int CHECK (day_of_month BETWEEN 1 AND 28),
  active                  boolean NOT NULL DEFAULT true,
  notes                   text,
  last_materialized_month text, -- 'YYYY-MM'; NULL = never materialized
  created_at              timestamptz NOT NULL DEFAULT now()
);

-- Income entries
CREATE TABLE income_entries (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id           uuid NOT NULL REFERENCES families,
  added_by            uuid REFERENCES profiles,
  source              text, -- 'salary'|'freelance'|'benefit'|'other'
  description         text,
  amount              numeric(10,2) NOT NULL,
  income_date         date NOT NULL,
  is_recurring          boolean DEFAULT false,
  recurrence_interval   text, -- 'monthly'|'weekly'
  people_transaction_id uuid REFERENCES people_transactions ON DELETE CASCADE, -- NULL if not linked to a People transaction
  created_at            timestamptz DEFAULT now()
);

-- Savings goals
CREATE TABLE savings_goals (
  id              uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id       uuid NOT NULL REFERENCES families,
  created_by      uuid REFERENCES profiles,
  name            text NOT NULL,
  target_amount   numeric(10,2),
  current_amount  numeric(10,2) DEFAULT 0,
  deadline        date,
  is_private      boolean DEFAULT false, -- if true, only creator can see
  created_at      timestamptz DEFAULT now()
);

-- Savings transaction ledger (deposits and withdrawals)
CREATE TABLE savings_contributions (
  id                uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  goal_id           uuid NOT NULL REFERENCES savings_goals ON DELETE CASCADE,
  family_id         uuid NOT NULL REFERENCES families ON DELETE CASCADE,
  added_by          uuid REFERENCES profiles,
  amount            numeric NOT NULL CHECK (amount > 0),
  transaction_type  text NOT NULL DEFAULT 'deposit', -- 'deposit'|'withdrawal'
  recovery_plan_id  uuid, -- set on deposits made toward a recovery plan
  note              text,
  contributed_at    date NOT NULL DEFAULT CURRENT_DATE,
  created_at        timestamptz DEFAULT now()
);

-- Plan for restoring money withdrawn from a savings goal
CREATE TABLE savings_recovery_plans (
  id                    uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id             uuid NOT NULL REFERENCES families ON DELETE CASCADE,
  goal_id               uuid NOT NULL REFERENCES savings_goals ON DELETE CASCADE,
  source_transaction_id uuid NOT NULL UNIQUE REFERENCES savings_contributions ON DELETE CASCADE,
  created_by            uuid REFERENCES profiles,
  target_amount         numeric(10,2) NOT NULL CHECK (target_amount > 0),
  monthly_amount        numeric(10,2) NOT NULL CHECK (monthly_amount > 0),
  deadline              date,
  status                text NOT NULL DEFAULT 'active', -- 'active'|'paused'|'completed'
  created_at            timestamptz DEFAULT now()
);

-- Monthly category budgets
CREATE TABLE budgets (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id    uuid NOT NULL REFERENCES families,
  category_id  uuid NOT NULL REFERENCES categories,
  month        date NOT NULL, -- always the 1st of the month
  amount       numeric(10,2) NOT NULL,
  created_at   timestamptz DEFAULT now(),
  UNIQUE(family_id, category_id, month)
);

-- Named contacts (family members, friends) for the People tracker
CREATE TABLE people (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  family_id   uuid NOT NULL REFERENCES families ON DELETE CASCADE,
  created_by  uuid REFERENCES profiles,
  name        text NOT NULL,
  notes       text,
  created_at  timestamptz DEFAULT now()
);

-- Money exchanges with a person — 6 types; expense/income auto-linked via FK
CREATE TABLE people_transactions (
  id               uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  person_id        uuid NOT NULL REFERENCES people ON DELETE CASCADE,
  family_id        uuid NOT NULL REFERENCES families ON DELETE CASCADE,
  added_by         uuid REFERENCES profiles,
  type             text NOT NULL CHECK(type IN ('sent', 'received', 'lent', 'borrowed', 'repaid_them', 'they_repaid')),
  amount           numeric(10,2) NOT NULL CHECK(amount > 0),
  note             text,
  transaction_date date NOT NULL,
  created_at       timestamptz DEFAULT now()
  -- Linked records live on expense_items.people_transaction_id and income_entries.people_transaction_id
  -- ON DELETE CASCADE ensures deletion is always atomic
);

Key design decisions

DecisionReason
UUID primary keysNo sequential IDs that can be guessed (security). Works across distributed inserts from mobile and web.
expense_items separate from receiptsOne receipt produces many items across multiple categories. Items can also be entered manually with no receipt.
is_private on savings_goalsFamily-wide visibility by default, but individual goals can be kept private. RLS enforces this.
Savings transaction RPCsDeposits, withdrawals, balance changes, and recovery-plan creation are committed atomically. Direct balance-changing writes are revoked so a failed request cannot leave savings_goals.current_amount out of sync with its ledger.
Recovery plans linked to withdrawalsA withdrawal may create one recovery plan. Later deposits link to that plan, making progress auditable without treating the withdrawal as an expense or pretending the savings were never used.
Soft category assignmentcategory_id is nullable — items can exist without a category while under review, and categories can be deleted without cascading item loss (items become uncategorized).
discount_amount + original_price on expense_itemsExtracted from receipt discount lines by the model and confirmed during review. Stored separately so the actual paid amount (amount) remains the authoritative financial figure. Displayed as a savings badge in the expense list.
User preferences as JSONBprofiles.preferences is a JSONB column with no fixed schema. New preference keys (e.g., showWeekFilter, showStoreFilter) are added by the app without DB migrations. Defaults are resolved in TypeScript via resolvePreferences() in packages/shared.
recurring_expenses as a template tableSeparates the recurring rule from its monthly occurrences. Instances are materialized into expense_items (with a recurring_expense_id FK) on page load. Editing or deleting a single month's entry does not affect the template or future entries.
On-load materialization for recurring expensesThe expenses page server component checks last_materialized_month vs. the current month and creates missing entries before returning the expense list. No Edge Function cron needed — simpler, no timezone issues, no retry logic required.
People tracker: atomic deletion via CASCADEWhen a people_transaction is deleted, its linked expense_item or income_entry is removed automatically via ON DELETE CASCADE on the FK. This eliminates orphaned records without two-step deletes. The user deletes from the People page only — expense/income entries with people_transaction_id set show a lock icon and block edit/delete.
People tracker: 6-type modelsent, lent, repaid_them auto-create an expense_item (money leaving). received, they_repaid auto-create an income_entry (money arriving). borrowed records a liability but creates no financial record — it's money you owe, not income. Balance = SUM(sign x amount) where negative = you owe them net.
Currency stored on families table, distributed via React ContextPer-family ISO 4217 code (EUR/USD/LKR/DKK; default EUR). Dashboard layout server component fetches the currency once and wraps all child layouts in CurrencyProvider. Every client component calls useFormatCurrency() — no prop threading needed. Server components call formatCurrency(amount, currency) directly. Module-scope helper components (e.g. BalancePill, RecurringRow) must each call useFormatCurrency() inside their own function body.
Pre-commit hook guards against Edit-tool truncationNTFS mount does not extend file size on write, so writing a longer string over a shorter one silently truncates the end of the file. .git/hooks/pre-commit rejects any staged .ts/.tsx file whose last byte is not 0x0a (newline). All file edits in this project use Python via bash to avoid the issue entirely.
Core Feature

Receipt Scanning Pipeline

Receipt scanning combines client-side image normalization and review with an authenticated server-side GPT extraction route. The user always confirms the structured result before Kotikassa saves financial data.

Processing steps

Step 1 — Normalize the Source Image

The web client accepts the selected receipt image, fixes its orientation, and compresses it to a JPEG within the route's size limit. Compression happens once before scanning.

  • The API accepts exactly one non-empty JPEG and verifies its magic bytes instead of trusting its filename or MIME header.
  • If the browser cannot decode a source format such as HEIC, the user receives an unsupported-format error instead of sending an unverified original.
  • The normalized blob stays in client state through review and is uploaded unchanged when the receipt is saved.

Step 2 — Authenticate, Authorize, and Rate-limit

POST /api/scan accepts a Supabase cookie session from the web app or a bearer access token from the future mobile flow. The server derives the user and family from that authenticated session, verifies the current privacy and receipt-scanning choice, and atomically consumes the family's durable scan quota before calling the provider.

Step 3 — Extract and Validate Structured Receipt Data

The server sends the JPEG to the configured OpenAI receipt model with store: false. Strict Structured Outputs define the JSON shape, and Zod performs the additional semantic and size validation needed by the application.

  • Required top-level data: store name, receipt date, printed total, and item rows.
  • Each item carries its final charged amount, quantity, supported unit, optional unit price, and discount fields.
  • The Finnish receipt prompt treats image text as data, preserves duplicate products, handles weighted and discounted lines, and excludes totals, VAT, payment, and membership rows.
  • Provider refusal, timeout, invalid image, rate limit, unreadable receipt, and schema failure return distinct stable API errors.

Step 4 — Categorize in the Client

Validated items are categorized by the active utility in packages/shared. Match priority:

  1. Family history — use the saved category for an exact product-name match
  2. Built-in Finnish dictionary — keyword match (e.g., "mansikka" → Groceries)
  3. Unmatched — item is left uncategorized, flagged for user review

Step 5 — Review and Save

The user sees the extracted store, date, total, items, quantities, prices, discounts, and category suggestions. They can:

  • ✏️ Edit the receipt or item fields
  • 🧠 Review explainable household-first item/store corrections; measured low-risk aliases may already be applied, but remain visible and immediately reversible
  • 🏷️ Change or assign a category
  • 🗑️ Remove an incorrect item
  • ➕ Add a missing item manually
  • ✅ Confirm and save the private image, receipt, expense rows, and scan telemetry

The save records the original validated model result, prompt/schema/model versions, token usage, latency, receipt line order, and user corrections. Versioned feedback events retain actor and source provenance; an unchanged save is recorded as save_only, not trusted as explicit confirmation. Category corrections update family memory. is_on_receipt describes label quality and is never treated as model-development consent.

Private household memory and global intelligence are separate scopes. Migration 042 projects versioned feedback into family-isolated item/store memory with support, rejection, undo, disagreement, recency, and confidence metadata. Missing expected feedback remains detectable on the receipt and safe retries cannot inflate support. A dry-run-first command backfills reliable legacy corrections.

A service-role-only refresh converts currently consent-eligible events into private aggregate global candidates with capped contributor influence and distinct receipt, contributor, household, and day counts. Migration 043 adds the only authenticated runtime boundary: it returns a minimal household-first suggestion projection without raw evidence or cross-household identities. Independent global patterns can support cold-start suggestions; one-household patterns are low-confidence, quality-gated, exposed only to a stable 20% cohort, and capped at three offers per household per day.

Migration 044 adds deterministic scan-quality detection without another model request. The scan API combines structural checks with an authenticated aggregate of the current household's own unit-price history, and review renders advisory warnings only beside suspicious fields. Corrected, dismissed, and unresolved outcomes plus review duration are stored on the receipt. Service-role-only views monitor quality by store/model/prompt and candidate contributor concentration; low-review or unresolved-warning receipts cannot strengthen the global candidate projection.

Migration 045 keeps learned automation disabled until the latest service-role-recorded fixed-holdout evaluation passes its scope-specific sample, precision, and expiry gate. Even then, only item/store aliases with strong recent conflict-free evidence qualify; global aliases additionally require independent support across at least three contributors and households. The authenticated projection exposes no evidence counts or identities. A private monitoring view tracks application and undo rates by policy, model, and prompt.

Suggestions never change price, quantity, unit, discount, item presence, deletion, or an ambiguous date. The review UI explains household, global, or deterministic-rule provenance behind click-to-reveal help, labels learned automatic applications, and records offered, accepted, rejected, and undone outcomes using feedback schema v2. Accepted suggestions replace the corresponding ordinary field-change event so one user action cannot inflate memory twice. See ADR-018.

Manual Entry Fallback

Manual expense entry remains available when the user declines receipt processing, the source format is unsupported, the provider is unavailable, or the user simply prefers not to scan:

  • As the user types, suggestions appear from their own purchase history + built-in Finnish grocery dictionary
  • Selecting a suggestion auto-fills the category from last use
  • Common items can be added in one tap
Legacy boundary: packages/ocr contains the superseded Tesseract worker, preprocessor, and parser from Phase 2. The active web scanner does not import them. They remain only until the labelled evaluation and production trial satisfy the Phase 9 removal gate. See ADR-015 for scanning, ADR-016 for model-development consent, and ADR-018 for correction-intelligence governance.

Engineering Standards

Code Standards & Principles

All code in Kotikassa follows SOLID principles, clean code practices, and TypeScript best practices. These are enforced through tooling (ESLint, TypeScript strict mode, pre-commit hooks) — not just by agreement.

SOLID Principles — applied to this codebase

S
Single Responsibility Principle
Every module, component, and function does exactly one thing. Receipt extraction, schema validation, deterministic reconciliation, categorization, review, and persistence stay separate.
For example, the scan route validates provider output, while the shared categorizer independently suggests categories for already validated items.
O
Open / Closed Principle
Code should be open for extension, closed for modification. The categorizer uses a pluggable keyword dictionary — adding a new category doesn't require changing the categorizer's logic, only adding entries to the dictionary.
e.g. CATEGORY_KEYWORDS is a config object. Adding "Health & Pharmacy" means adding one entry — no changes to categorize().
L
Liskov Substitution Principle
Interfaces define contracts that implementations must honour. The ExpenseRepository interface works whether the implementation queries Supabase, a test fixture, or local storage — without the caller knowing the difference.
e.g. Tests use a MockExpenseRepository that satisfies the same TypeScript interface as the real Supabase one.
I
Interface Segregation Principle
Many focused interfaces are better than one large one. A component that only displays expense data shouldn't be forced to depend on functions that create or delete expenses.
e.g. ExpenseReader and ExpenseWriter are separate interfaces. Read-only views only receive a reader.
D
Dependency Inversion Principle
High-level modules (UI components, business logic) depend on stable contracts rather than concrete providers (Supabase or OpenAI). This keeps aggregation, review, and validation logic testable and replaceable.
e.g. useExpenses(repo: ExpenseRepository) — the hook receives its data source, so tests inject a mock without touching Supabase.
