Replacing Tesseract with

What changes, what stays, what gets deleted, and why — the complete picture before implementation.

The Problem

Why Tesseract was chosen — and why it has to go

Tesseract.js was chosen for one specific reason: it runs entirely inside the browser as a WebWorker. No server needed, no receipt photo leaves the device. That was the right call at the time.

The problem is accuracy. Tesseract reads each character in isolation — it has no understanding of language or context. On Finnish thermal receipts it makes systematic mistakes:

What the receipt saysWhat Tesseract readsWhy
0,52 € 8,52 € Thermal printing makes "0" slightly thicker — Tesseract sees a crossbar and reads "8"
MILKA OREO 100G 1,00 F item missed entirely The "F" VAT code suffix blocked the price regex — required a parser hotfix
E 25,5 ... (ALV row) £ 0 87 (parsed as item) 43% confidence — OCR garbled the ALV breakdown line, required another skip pattern
PRISMA SAVONLINNA first item line instead Store header not matched — fell through to heuristic, which grabbed wrong line

Every new store format requires another regex fix in parser.ts. There is no end to this.

The Decision

Replace the entire OCR + parser pipeline with GPT-4o mini Vision

GPT-4o mini accepts the receipt photo directly and returns structured JSON. It understands Finnish natively, knows that YHTEENSÄ is a total not an item, handles VAT codes, reads context across lines, and works with any store layout without needing a parser rule for each one.

Training Data Strategy

How you collect training data for a future own model

The goal of eventually replacing GPT with your own model (like Donut) is still achievable — the strategy just changes.

Old approach (Tesseract world) — no longer valid

Collect text correction pairs: what Tesseract said → what user corrected. Train a language model to fix Tesseract's text output.

Problem: Tesseract text is not the goal. The goal is receipt image → structured JSON.

New approach (GPT world) — collect reproducible image labels

Each saved scan can produce a training pair when the image upload succeeds and every included label is confirmed as visible in the receipt:

Training input Training output Where stored
Receipt photo Correct structured items receipts.image_url + expense_items joined on receipt_id

Phase 9 adds scan provenance, the validated original model result, deterministic line order, and an is_on_receipt label. Roughly 500 receipts is an initial collection target followed by evaluation, not a guarantee that a specific future model is ready.

Critical export filters — do not omit

FilterWhy it matters
WHERE r.status = 'confirmed' Excludes abandoned uploads where the user never completed the save flow
AND e.is_on_receipt = TRUE Includes GPT items and manually added lines that GPT missed, while excluding extras not visible in the image. is_manual remains provenance only.
AND r.image_url IS NOT NULL Excludes saved receipts whose Storage upload failed and therefore have no training image.
HAVING COUNT(e.id) > 0 Excludes receipts where the user deleted every item on the review screen

Image access: receipts.image_url stores a Supabase Storage path (e.g. familyId/1234.jpg), not a public URL. Downloading images for model-development export requires the service role key — use it from a server-side script, never from client code. See ADR-016, migrations 029–031, and docs/setup.md for the governed export process.

The Exit from GPT Dependency

The dataset grows through reviewed scans, but model readiness depends on diversity, image quality, labels and held-out evaluation. Donut is one possible future option, not a guaranteed choice or timeline.

Privacy

What changes about where receipt data goes

Today (Tesseract)

Receipt photo is processed entirely inside the user's browser. The image never leaves the device for OCR. Only the extracted text and item data go to Supabase.

After (GPT-4o mini)

The compressed receipt photo is sent to OpenAI's API servers for processing with application storage disabled. OpenAI's API data is not used for model training by default; applicable abuse-monitoring logs may be retained for up to 30 days. The confirmed image is also stored in Supabase Storage.

For a family budgeting app, this trade-off is acceptable. If privacy is a hard requirement in the future, the own-model path (Donut on your own server) restores full privacy.

Resilience

What happens when GPT is unavailable

OpenAI's API has occasional downtime. The scan route should handle this gracefully.

Fallback strategy

The /api/scan route returns a clear error if the OpenAI call fails. ReceiptScanner.tsx catches this and shows the user a message: "Automatic scanning is temporarily unavailable. You can add items manually."

Tesseract is not kept as a silent code fallback — maintaining two OCR paths adds complexity and the Tesseract path produces poor results anyway. The manual entry fallback is the right answer.

Why not keep Tesseract as fallback?

Tesseract produces incorrect data that users then have to fix. Showing the user wrong items silently is worse than showing a clear "unavailable" message. A bad fallback is worse than no fallback.
